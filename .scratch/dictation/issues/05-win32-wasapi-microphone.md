# 05 Win32: microphone capture through hand-written WASAPI, shared WAV writer

Status: ready-for-agent
Blocked by: 01

Spec: `.scratch/dictation/spec.md` → Microphone, user stories 8, 32, 39. Notes: `wasapi-capture.md` in the shared notes directory (interfaces, GUIDs, vtable order, flags, the COM source-generator recipe).

## Goal

`TryOpenMicrophone()` and `CloseMicrophone()` in `Win32Platform.Microphone.cs` capture 16 kHz 16-bit mono PCM from the Default Communication Device through WASAPI shared mode with no package, and the WAV container writer that `ClickSound` already contains is extracted into a core `Wav` type that both the click and the microphone clip use. Files: `Win32Platform.Microphone.cs`, new files under `Win32/Audio/` for the COM interfaces and the capture loop, new `Core/Wav.cs`, `Core/ClickSound.cs` (use `Wav`), the app csproj (`AllowUnsafeBlocks`, needed by the COM source generator), and a new `WavTests.cs`. No other file changes.

## Behaviour

- `Wav.FromPcm16(byte[] pcm16, int sampleRate, short channels)` returns a complete RIFF/WAVE byte array (fmt chunk: PCM, channels, rate, byte rate, block align, 16 bits; data chunk). `ClickSound.Wav()` builds its samples as today and hands them to `Wav`; its bytes must not change (assert against the current output in a test, for example its length and the fmt fields).
- `TryOpenMicrophone`: create the device enumerator, `GetDefaultAudioEndpoint(eCapture, eCommunications)`, activate `IAudioClient`, `Initialize` shared with `EVENTCALLBACK | AUTOCONVERTPCM | SRC_DEFAULT_QUALITY` and the 16 kHz mono format (the rate is a constant in one place so a later transport can change it), set the event handle, get `IAudioCaptureClient`, `Start`, and run a background thread that waits on the event and drains packets into a `MemoryStream` (silent packets written as zeros). Any failure (no device, `E_NOTFOUND`, an HRESULT from `Initialize`) releases what was created and returns false. The device is opened per call; nothing is cached between Dictations.
- `CloseMicrophone`: signal the thread to stop, `Stop` the client, join the thread, release every COM object and the event, and return `new AudioClip(bytes, 16000)`. Calling it when nothing is open returns an empty clip.
- COM interfaces as `[GeneratedComInterface]` partial interfaces with `[Guid]`, methods in vtable order, unused slots declared with plain signatures; the enumerator created with `CoCreateInstance` and wrapped with `StrategyBasedComWrappers`. Use `[PreserveSig]` HRESULT returns where a failure is expected (`GetDefaultAudioEndpoint`, `Initialize`) so `E_NOTFOUND` is a return value, not an exception.
- Everything that touches the first `IAudioClient` call happens on the thread that calls `TryOpenMicrophone` (the message loop, STA); only the drain loop runs on the worker.

## Tests

`WavTests.cs`: header fields for a known buffer (RIFF size, fmt values, data size); an empty buffer gives a 44-byte file; `ClickSound.Wav()` still starts with `RIFF`, is 44 bytes plus its sample count times two, and declares 44100 Hz mono 16-bit. The WASAPI code is not unit tested; record in Comments whether a debug-run recording was listened to or at least produced a non-empty, non-silent clip.

## Comments
- Built on branch `worktree-agent-aab2b68c0bee08367` in `05:` commits; `dotnet build` 0 warnings, `dotnet test` 92 green (88 plus four in `WavTests`: a known 16 kHz mono buffer's header fields and payload, the empty buffer's 44 bytes, stereo at 44.1 kHz for the channels parameter, and the click pinned at `RIFF`, 2690 bytes, 44100 Hz mono 16-bit). `Core/Wav.cs`: `public static byte[] Wav.FromPcm16(byte[] pcm16, int sampleRate, short channels)` returns the complete file, and `Wav.HeaderLength` is 44; tickets 06 and 08 should call `Wav.FromPcm16(clip.Pcm16, clip.SampleRate, channels: 1)` for the multipart `file` part of an `AudioClip`. `ClickSound.Wav()` goes through it and its bytes are identical (SHA-256 compared before and after; the test file does not keep the hash). WASAPI: `Win32/Audio/WasapiInterfaces.cs` holds the four `[GeneratedComInterface]` interfaces in vtable order and `WaveFormatEx`, GUIDs and vtables checked against the 10.0.26100 SDK headers (they match the notes); `Win32/Audio/NativeMethods.Audio.cs` is a `NativeMethods` partial with the Core Audio constants and `CoCreateInstance`; `Win32/Audio/WasapiCapture.cs` is the capture (`TryOpen(sampleRate)` on the caller's thread, the drain loop on an MTA background thread named `Microphone drain`, `Close()` returning the PCM bytes); `Win32Platform.Microphone.cs` holds one `WasapiCapture?` and `MicrophoneSampleRate = 16000`, and `CloseMicrophone()` with nothing open returns an empty clip. Deviations from the notes: every method we call is `[PreserveSig] int` (not only `GetDefaultAudioEndpoint` and `Initialize`), so `TryOpen` has no catch; interface pointers come out as `nint` and are wrapped with `CreateObjectFlags.UniqueInstance`, because `ComObject.FinalRelease` only releases unique instances; the event is a .NET `AutoResetEvent` whose handle goes to `SetEventHandle` (no `CreateEventW`); `hnsBufferDuration` is half a second rather than 0 so a late worker loses no packet; the enumerator and device are released at the end of `TryOpen` since the stream no longer needs them, the client, capture client and event at `Close`; `TryOpenMicrophone` closes a stray open capture first. Exercised: a throwaway console harness in the scratchpad (compiled from the `Win32/Audio` sources, `[STAThread]` Main, no window, no input) opened the Default Communication Device, recorded 1.0 s and closed: 32248 bytes = 16124 samples = 1.01 s at 16 kHz, 3710 samples non-zero, peak amplitude 1 of 32767; a second open after the first close succeeded (0.2 s, 6328 bytes); the process exited and nothing was saved. So the device opens, the engine converts to the requested format, the stream drains and releases, and the data is live rather than digital silence, but nobody spoke and the level was not confirmed: the clip was not listened to. Not exercised: `E_NOTFOUND` with no capture endpoint, `E_ACCESSDENIED` from the microphone privacy setting (both reach the core as `No microphone found`), a device removed mid-Listening (the drain loop ends on the first failing call and `Close` returns what it has), and the real message loop (ticket 03/04 paths).
